# Налить раскладов задним числом

> актуально · 2026-09-11 · `pnpm run seed` создаёт расклады на прошлых якорях через публичный API; сверяет их крон, первые звёзды появляются примерно через двадцать минут

Звёзды в карточке гадалки считаются по сверенным раскладам, и на пустой базе их нет вовсе. История наливается один раз — руками.

1. `pnpm run seed -- --base https://tarotalpha.<аккаунт>.workers.dev` — 120 раскладов: пять инструментов по 24 якоря с шагом восемь часов. Без `--base` льёт в `http://localhost:8787`.
2. Ждать. Крон берёт пять раскладов каждые десять минут: десять сверок (звёзды появляются) — через двадцать минут, все сто двадцать — часа за четыре.
3. Проверить: `curl https://tarotalpha.<аккаунт>.workers.dev/api/readers` — в ответе `verdicts` растёт, у каждой гадалки `stars` и `wins`.

Флаги: `--assets` (через запятую), `--per-asset`, `--every` (часов между якорями), `--steps` (дней в раскладе), `--pause` (лимит API — 60 запросов в минуту с адреса, меньше 1.1 с ставить нельзя).

Что нужно знать:

- **Якоря скрипт берёт уже созревшие** — от последнего закрытого часа минус горизонт, дальше в прошлое. Незрелый расклад крон просто не тронет.
- **Гадалка у всех раскладов `atr`, и это ни на что не влияет:** сверка судит всех пятерых сразу, поле `reader` решает только, чей прогноз покажет ссылка.
- **Отказы биржи — это нормально:** якорь старше, чем провайдер отдаёт по инструменту, даёт 422, скрипт печатает строку и идёт дальше.
- **Расклады получаются настоящие:** у каждого есть `/r/:id`, они ничем не помечены и живут в общей таблице. Событий воронки они не пишут.
- Заливать повторно можно: якоря те же, но `id` новые, поэтому в базе появятся дубли раскладов и счёт станет вдвое длиннее. Лучше долить другими `--assets`.

Скрипт — `scripts/seed_readings.py`. Как считается рейтинг — `../flows/reading-lifecycle.md`, почему так — `../adr/0007-reader-rating-by-places.md`.
