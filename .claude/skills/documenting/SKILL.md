# Как здесь документируют

Проза по-русски, код и комментарии по-английски. Оснастка в `scripts/` — исключение, линтер изымает её от `LNG001`.

## Шаг 0. Документ описывает «сейчас»

Первое правило, остальные после него. Документ и комментарий говорят, как устроено и почему — на момент чтения. Не «раньше было», «сначала решили X, потом Y», «переименовано», «убрали» — это `git log`. Не «будет» — это GitHub Issues. Не «сделано/осталось» — это PR. Правка, из-за которой текст начал врать, чинит его в том же PR; «обновим потом» не бывает.

«Почему» остаётся, если оно про устройство, а не про историю: лимит, цена, поведение чужой системы, отвергнутый вариант и чем он плох. «Крон берёт пять раскладов: у него 10 мс CPU, сверка стола стоит миллисекунду» — документ. «Сначала крон брал десять, потом урезали» — `git log`.

## Шаг 1. Нужен ли документ вообще

Три фильтра, в этом порядке. Сработал любой — документа нет.

1. **Выводится из кода?** Не документируем: список полей и эндпоинтов устаревает в тот же день.
2. **Это состояние?** «Что сделано» — PR и `git log`, «что осталось» — issue; в документ ни то ни другое не идёт.
3. **Восстанавливается по коду за минуту?** Не документируем.

Документируем только то, что **из кода не восстанавливается никогда**:

- поведение чужих систем — «Binance отдаёт klines пачками по 1000, лимит веса 6000/мин на IP»;
- отвергнутые варианты и цену решения — иначе их переизобретут;
- инварианты между частями, не выраженные типом;
- процедуры с ручными шагами и последствиями снаружи;
- потоки данных: что чем триггерится, откуда берёт, куда отдаёт.

**Issue — не хранилище знания.** Задача — след работы. Что понадобится через полгода, живёт в доке своей области. Номер issue допустим как метка («#12»), но не как ссылка, без которой текст непонятен.

## Шаг 2. Куда

Доков мало, и каждый закрывает свою область целиком: как устроено, почему так, что отвергли и чем платим, как сделать руками, факты о чужих системах этой области. Список областей — `docs/README.md`. Читатель открывает один док и находит там всё по своему вопросу.

| Что | Куда |
| --- | --- |
| как работает, ≤3 строк | комментарий у кода |
| как работает, длиннее; почему так; что отвергли | раздел в доке области + ссылка из кода |
| как сделать руками | раздел в доке области |
| факт о чужой системе | раздел в доке области, которая с ней говорит |
| что значит слово | `docs/glossary.md` |
| что изменилось | заголовок коммита и описание PR |
| что делать дальше | issue в GitHub |

Новый док — только под область, которую не закрывает ни один существующий. Сомневаешься — раздел в существующем.

## Шаг 3. Сколько

- **Шапка файла — до 10 строк.** Только первый блок **выше кода**; импорты и директивы кодом не считаются. Отвечает на «что это и почему так устроено», содержимое файла не пересказывает.
- **Всё остальное — до 3 строк.** Один комментарий на секцию, и только о том, чего не видно в коде: «сделано так, потому что», «работает только при», «здесь грабли».
- **Режется без разговора:** шапка, пересказывающая сигнатуры; ченджлог в любом виде; список шагов, который и есть код ниже; вода — фраза, после удаления которой читатель не теряет ни факта, ни причины. Отвергнутый вариант остаётся: «X стоил бы Y».
- Не влезло — раздел в доке области и ссылка из кода в одну строку.
- **Ссылка двусторонняя:** комментарий даёт путь к документу, документ называет свои файлы. Обе стороны проверяет линтер (`CMT003`, `MD004`).

Escape hatch: `docs-lint: allow` внутри блока — для текста, который обязан стоять ровно здесь. Обходить им требование сокращать нельзя.

## Шаг 4. Форма документа

Вторая строка любого дока в `docs/` — статус, дата, вердикт одним предложением:

```markdown
# Как считается прогноз

> актуально · 2026-09-12 · сид даёт три карты дня, одни на всех гадалок; гадалка превращает их в 24 свечи своей формулой
```

| Статус | Значит |
| --- | --- |
| `актуально` | описывает работающий код, правится вместе с ним |
| `черновик` | кода ещё нет, читать как замысел |

Других статусов нет. Док, который врёт, не помечают, а чинят; область исчезла из кода — док удаляют и переводят ссылки.

- **`docs/` плоская.** Одна папка, `docs/README.md` — строка на документ: какие вопросы он закрывает.
- **Имя файла — область**, которую док закрывает: `engine.md` для `engine/`, `reading-lifecycle.md` для жизни расклада.
- **Секретов в тексте нет.**
- **Термины бери из `docs/glossary.md`**, на месте их не изобретают.

## Шаг 5. Нейминг кода: имя — это обещание

В имени стоит то, **что происходит**. Слой, тип и тема в имя не идут.

| Плохо | Почему | Хорошо |
| --- | --- | --- |
| `utils.ts`, `helpers.ts` | ничего не обещает | `slugify.ts`, `atr.ts` |
| `handleData()` | слой + тип | `mergeKlines()` |
| `ReadingManager` | «менеджер» — не действие | `ReadingTeardown` |

Тест: **имя обещает ровно то, что внутри, и ничего сверх?** Один термин — одно имя во всей кодбазе.

## Шаг 6. Перед тем, как закрыть задачу

**Доки, которые ты не трогал, могли начать врать.** Шаг полного пути (`CLAUDE.md`, «Порядок работы»):

```bash
pnpm run related
```

Команда выдаёт документы, говорящие о том же, что изменил PR. По каждому хватает вердикта во второй строке; целиком открываешь только тот, что про сделанное, и отвечаешь: **противоречит ли он сделанному?** Противоречит — правь в этом же PR. Не про это — ничего.

Линтер найдёт мёртвую ссылку, но не найдёт двух документов, утверждающих разное. Это работа читателя.

## Проверка

| код | что |
| --- | --- |
| CMT001 | блок комментариев: шапка файла > 10 строк, в теле > 3 |
| CMT002 | то же для python-docstring |
| CMT003 | код ссылается на несуществующий документ |
| MD001 | markdown вне `docs/` и `.claude/` |
| MD002 | док не вписан в `docs/README.md` |
| MD003 | нет строки «статус · дата · вердикт» или статус не из двух |
| MD004 | док ссылается на несуществующий путь |
| MD005 | PR тронул файлы, которые док зовёт своими, док не обновлён |
| LNG001 | кириллица в комментарии кода |
| NAM001 | имя файла или папки ничего не говорит |
